# 개발 흐름

프로젝트가 어떤 순서로 바뀌었는지와 각 단계의 상세 문서를 안내한다. 문서는 종류보다 개발 단계로 묶는다. 기존 설계·계획 본문은 당시 기록으로 유지하며, 현재 상태까지 갱신된 문서는 아래에 따로 표시한다.

| 단계 | 시기 | 주요 변화 | 상세 문서 |
|---|---|---|---|
| 01. 초기 MVP | 2026-10-22 | 곡 검색·저장, 태그 조합 조회, 태그·그룹 관리. 브라우저 IndexedDB에 저장 | [설계](01-초기-MVP/설계.md), [구현 계획](01-초기-MVP/구현-계획.md) |
| 02. 데이터 모델 개선 | 2026-10-29~30 | 공통 곡과 사용자별 태그·그룹을 분리. 꺼내기 목록에서 곡의 태그 편집 추가 | [데이터 모델](02-데이터-모델-개선/데이터-모델.md) |
| 03. 서버 DB 전환 | 계획 2026-11-06, 구현 2026-11-09 | Node.js + Fastify + SQLite로 저장 위치를 옮기고 HTTP API 연결 | [계획과 검증](03-서버-DB-전환/계획과-검증.md) |

## 01. 초기 MVP — 기본 사용 흐름 만들기

iTunes에서 곡을 찾아 태그를 달고, 태그 조합으로 다시 꺼내는 흐름을 만들었다. 같은 그룹 안은 OR, 다른 그룹끼리는 AND로 필터링하며 재생은 유튜브 검색 링크로 연결했다.

- [설계](01-초기-MVP/설계.md): 만들려는 이유, 범위, 화면 동작과 기술 선택.
- [구현 계획](01-초기-MVP/구현-계획.md): 도메인·저장소·화면별 구현 순서와 검증 시나리오. 초기 계획이며 현재 완료 상태를 나타내는 체크리스트는 아니다.

## 02. 데이터 모델 개선 — 공통 곡과 개인 태그 분리

곡 정보는 공통으로 두고 태그·그룹·곡–태그 연결은 사용자별로 관리하도록 바꿨다. 곡 삭제 UI를 제거하고 표시 제목은 공통으로 수정하도록 했다. 이어 꺼내기 목록에서도 곡의 태그를 붙이거나 뗄 수 있게 했다.

- [데이터 모델](02-데이터-모델-개선/데이터-모델.md): 데이터 구조, 사용자 경계, 저장소·화면 동작과 검증 기준.
- 이 문서는 2026-10-29에 시작했으며, 3단계의 SQLite 전환까지 반영한 **현재 데이터 구조 문서**로도 사용한다.
- 꺼내기 목록의 태그 편집은 별도 상세 문서가 없으며, 구현 이력은 2026-10-30 커밋과 PR #2에 남아 있다.

## 03. 서버 DB 전환 — 브라우저 밖에 데이터 보관

브라우저 IndexedDB 대신 서버 SQLite에 저장하도록 바꿨다. React 화면은 HTTP 저장소를 통해 API를 호출하며 현재는 기본 사용자 한 명으로 동작한다.

- [계획과 검증](03-서버-DB-전환/계획과-검증.md): 전환 범위, 작업별 완료 상태, 실제 구현과 검증 결과를 함께 기록한다.
- 구현·자동 검증과 실제 API 서버 재시작 후 데이터 유지는 확인했다.
- 기존 브라우저 데이터는 이전하지 않기로 결정했다. 2026-11-15 사용자가 전체 브라우저 수동 확인과 브라우저 재실행 후 데이터 유지를 확인했다. 홈서버 배포는 후속 작업이다.

## 다음 작업과 문서 관리

[이후 할 일](90.이후-할-일.md)에서 다음 작업, 보류한 결정과 미검증 항목을 관리한다. 아직 시작하지 않은 작업을 완료된 개발 단계에 넣지는 않는다.

새로운 개발 단계를 시작하면 다음 번호의 폴더를 만들고 이 문서에 요약과 링크를 추가한다. 단계 안에서는 `설계.md`, `구현-계획.md`, `구현-결과.md`처럼 내용을 알 수 있는 이름을 쓰되, 기존 문서에 계획과 결과가 함께 있으면 억지로 나누지 않는다. 여러 단계에 걸친 할 일은 공통 목록에 유지한다.
