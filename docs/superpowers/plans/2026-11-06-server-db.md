# 서버 DB 전환 계획

작성일: 2026-11-06
상태: 서버 DB 전환 구현 및 자동 검증 완료. 기존 데이터는 이전하지 않기로 결정. 사용자 브라우저 수동 확인 및 브라우저 재실행 검증 완료.
갱신일: 2026-11-15
작업 브랜치: `feat/server-db`

## 목표와 선택

곡·태그·그룹 데이터의 저장 위치를 브라우저 IndexedDB에서 서버 SQLite DB로 바꾼다. 기존 React 화면과 도메인 로직을 최대한 유지하며, 로컬 개발 환경에서 API 서버와 앱을 실행해 저장·조회·수정과 서버 재시작 후 데이터 유지를 확인한다. 홈서버 배포는 별도 후속 작업이다.

- 백엔드: Node.js + TypeScript + Fastify.
- DB: SQLite. 별도 DB 서버 없이 서버가 실행되는 컴퓨터의 파일로 저장한다.
- 프런트엔드: 기존 React 앱과 `SongRepository` 인터페이스를 유지한다.
- 브라우저 저장소 대신 `fetch`를 사용하는 `HttpSongRepository`를 추가하고 `src/main.tsx`에서 연결한다.
- Spring 서버 전환은 이번 범위에서 제외한다.

```text
브라우저의 React 앱 → HTTP API → Node.js 서버 → SQLite
```

## 유지할 동작과 데이터

- [현재 데이터 모델](../../design/data-model-redesign.md)의 `users`, `songs`, `tags`, `groups`, `songTags` 구조를 SQL 테이블로 옮긴다.
- 곡 정보는 공통이며 태그·그룹·곡–태그 연결은 사용자별로 관리한다.
- 초기에는 기본 사용자 한 명으로 사용한다. 사용자 ID는 서버에서 결정하고 요청의 임의 사용자 ID를 신뢰하지 않는다.
- 이름 정규화, 중복 처리, 참조·소유권 검사, 삭제 시 연결 정리, 최근 사용 시각 갱신을 유지한다.
- 곡 검색과 유튜브 검색 링크 재생은 기존 구현을 유지한다.
- 클라이언트는 같은 서버 DB를 조회한다. 재조회·새로고침으로 변경을 확인하며, 여러 기기 외부 접속과 실시간 반영은 후속 작업으로 둔다.
- 기존 `music-tag-v2` IndexedDB 데이터는 삭제하지 않는다. 2026-11-15 사용자 결정에 따라 서버로 이전하지 않고 기존 IndexedDB를 보존한다.

## 진행 순서와 완료 기준

### 1. SQLite 저장소

- [x] 서버 코드와 실행·개발 명령을 추가했다. Node 26 내장 `node:sqlite`의 `DatabaseSync`와 `tsx`를 사용한다.
- [x] 테이블·제약 조건·외래키와 스키마 마이그레이션을 구현한다. 이후 변경 시 기존 데이터를 보존한다.
- [x] SQL 저장소에 기존 `SongRepository`의 동작을 구현한다.
- [x] 여러 테이블을 변경하는 작업은 트랜잭션으로 처리한다.
- [x] 기존 Dexie 저장소 테스트의 검증 항목을 활용해 중복·사용자 경계·삭제·롤백·재시작 후 데이터 유지를 검증한다.

### 2. API와 프런트엔드 연결

- [x] 저장소의 조회·변경 작업을 제공하는 API와 요청 검증을 구현한다.
- [x] 도메인 오류를 HTTP 응답으로 변환하고, 클라이언트에서 기존 오류 타입으로 복원한다.
- [x] `HttpSongRepository`를 추가하고 앱 초기화를 전환한다.
- [x] 저장 실패·접속 실패를 화면에 표시하고 재시도할 수 있게 한다. 실패한 변경을 성공으로 표시하지 않는다.
- [x] API 통합 테스트와 HTTP 저장소 테스트로 주요 성공·실패 흐름을 확인한다.

### 3. 기존 데이터 처리와 로컬 검증

- [x] 2026-11-15 사용자 결정: 기존 브라우저 데이터는 이전하지 않는다. 가져오기·중복 처리 구현은 필요 없다. 현재 앱은 기존 IndexedDB를 읽거나 삭제하지 않고 SQLite DB를 사용한다.
- [x] 로컬 개발용 API는 기본적으로 루프백 주소에 바인딩하고, 개발 시 프런트엔드의 `/api` 요청을 API 서버로 전달하도록 설정한다.
- [x] DB 파일 경로를 설정할 수 있게 하고, DB 파일을 Git 추적 대상에서 제외한다.
- [x] README에 프런트엔드·API 실행 방법, DB 저장 위치와 기존 데이터 처리 방침을 기록한다.
- [x] 2026-11-15 사용자가 실제 브라우저에서 검색·저장·제목 수정·태그·그룹 관리·태그 필터·유튜브 재생 링크와 실제 키보드 한글 조합 중 엔터 처리를 모두 확인했다.
- [x] 실제 API 서버와 Vite를 실행해 `/api` 프록시 연결, 곡·태그·그룹 저장과 서버 재시작 후 연결 유지를 확인했다.
- [x] 2026-11-15 사용자가 브라우저를 완전히 종료하고 같은 주소로 다시 접속해 곡·태그·그룹·수정한 제목이 유지되는지 확인했다.

## 작업 원칙과 후속 범위

- 구현은 대상 옆에 테스트를 먼저 작성하고 실패를 확인한 뒤 진행한다.
- 각 구현 작업을 마칠 때 `npm test`, `npm run lint`, `npm run build`를 모두 통과시킨다.
- 홈서버 설정·배포, 공유기·도메인·HTTPS·외부 접속, 접근 인증, 정기 백업·복원과 운영 절차는 이번 완료 기준에서 제외하고 후속 작업으로 둔다. 외부 공개 전에는 접근 인증을 마련한다.
- 기존 데이터 이전용 JSON 내보내기·가져오기는 구현하지 않는다. 서버 DB 백업·복원과 백업 UI는 후속 작업으로 둔다.
- PostgreSQL 전환, 여러 사용자 로그인, 실시간 동기화, 모바일 화면 개선은 후속 작업으로 둔다.

## 구현 결과와 검증 기록

- `server/sqliteRepository.ts`: 스키마 버전 1 초기화, 외래키·사용자 범위 제약과 트랜잭션. 상위 스키마 버전은 거절한다.
- `server/app.ts`: Fastify API, 요청 검증과 도메인 오류 응답. 현재 사용자 ID는 서버에서 `default`로 결정한다.
- `server/main.ts`: DB 경로·포트 설정, 루프백 바인딩과 종료 처리.
- `src/adapters/httpRepository.ts`, `src/main.tsx`: HTTP 저장소와 앱 연결. 기존 IndexedDB 초기화는 앱 시작 경로에서 호출하지 않는다.
- UI: 저장·조회 실패와 재시도, 저장 성공 후 조회 실패 시 조회만 재시도. 연속으로 들어온 변경 작업은 순서대로 처리한다.
- `npm test`: 17개 파일, 133개 테스트 통과. SQLite 저장소, API, HTTP 저장소, UI 오류·재시도와 기존 동작을 검증했다.
- `npm run lint`, `npm run build`: 통과.
- 실제 프로세스 검증: 임시 DB 디렉터리 생성, Vite 프록시를 통한 API 쓰기와 API 서버 재시작 후 곡·태그·그룹 연결 유지를 확인했다. 실제 브라우저 수동 검증과 구분한다.

### 2026-11-15 브라우저 저장 오류 수정

- 사용자 브라우저 확인 중 저장 실패 메시지가 반복되는 문제를 발견했다. HTTP 저장소의 기본 `fetch`를 전역 객체에 바인딩하도록 수정했다.
- 호출 대상이 잘못되면 `Illegal invocation`으로 실패하는 재현 테스트를 먼저 추가하고 실패를 확인한 뒤 수정했다. 수정 후 17개 파일, 134개 테스트와 lint·build가 통과했다.
- 별도 임시 SQLite DB를 사용하는 검증 화면에서 사용자가 수정 후 정상 동작을 확인했다. 이후 사용자가 안내한 전체 수동 확인 항목과 브라우저 재실행 후 데이터 유지까지 모두 확인했다고 보고했다.
